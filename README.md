# Discord-бот заявок в команду проекта

Бот для подачи и модерации заявок (режимы **RW** и **FT**) с persistent-кнопками,
SQLite-хранилищем и автоматическим снятием роли отказа через 7 дней.

**Написано под `discord.py == 2.7.1`** (см. `requirements.txt`). Используются
`discord.ui.DynamicItem` (доступен с 2.4) и `app_commands`.

---

## Возможности

- Панель с кнопкой «📋 Подать заявку» — создаётся один раз и переживает перезапуски.
- Выбор режима через Select Menu в ephemeral-сообщении, затем Modal с формой.
- Серверная валидация возраста (целое число, от 14 лет) — до записи в БД.
- Защита от дубликатов: одна Pending-заявка на пользователя (одобренная заявка
  повторной подаче не мешает).
- Cooldown 7 дней после отказа — хранится в SQLite, а не в памяти и не в роли.
- Кнопки «🟢 Одобрить» / «🔴 Отказать» работают после перезапуска бота.
- Проверка прав модерации (настраиваемая) на стороне сервера.
- Автоснятие роли отказа фоновой задачей `tasks.loop` раз в минуту.
- Полное логирование в консоль и `bot.log` (с ротацией) и traceback для исключений.

```
├── .env.example
├── .gitignore
└── README.md
```

Структура из ТЗ сохранена. Дополнений два, оба минимальные:

1. **Таблица `settings`** в SQLite — хранит `message_id` и `channel_id` панели.
   Без этого после перезапуска невозможно узнать, существует ли панель, и бот
   плодил бы дубликаты.
2. **Функции `delete_application()`, `set_application_message_id()`,
   `get_application()`, `get_last_application()`, `get_setting()/set_setting()`**
   в дополнение к перечисленным в ТЗ — нужны для отката неудачной отправки,
   сохранения `message_id` и явной обработки статуса `Approved`.

## Настройка `.env`

```bash
cp .env.example .env
```

Заполните значения (включите в Discord «Настройки → Расширенные → Режим разработчика»,
затем ПКМ по серверу / каналу / роли → «Копировать ID»):

| Переменная | Что это |
|---|---|
| `DISCORD_TOKEN` | Токен бота из Developer Portal |
| `GUILD_ID` | ID вашего сервера |
| `APPLICATION_PANEL_CHANNEL_ID` | Канал с панелью подачи |
| `RW_APPLICATION_CHANNEL_ID` | Канал заявок режима RW |
| `FT_APPLICATION_CHANNEL_ID` | Канал заявок режима FT |
| `CANDIDATE_ROLE_ID` | Роль «Кандидат» (выдаётся при одобрении) |
| `REJECTED_ROLE_ID` | Роль отказа (снимается автоматически) |
| `REJECTION_COOLDOWN_DAYS` | Кулдаун после отказа, по умолчанию 7 |
| `MIN_AGE` | Минимальный возраст, по умолчанию 14 |
| `BLOCK_AFTER_APPROVAL` | `false` (по умолч.) — после одобрения можно подать заявку снова |
| `MODERATOR_PERMISSIONS` | Права для кнопок модерации, например `manage_guild,administrator` |
| `MODERATOR_ROLE_IDS` | (опц.) ID ролей модерации через запятую |

Если обязательная переменная отсутствует или некорректна, бот **не запустится** и
выведет список проблем.

## Настройки в Discord Developer Portal

1. **Applications → ваше приложение → Bot**
   - «Reset Token» → скопируйте токен в `.env` (нигде больше его не храните).
   - **Privileged Gateway Intents → SERVER MEMBERS INTENT → ВКЛЮЧИТЬ.**
     Он нужен, чтобы получать участников и выдавать/снимать роли.
   - `MESSAGE CONTENT INTENT` и `PRESENCE INTENT` включать **не нужно**.

   В коде запрашивается минимум: `guilds` + `members`.

2. **OAuth2 → URL Generator**
   - Scopes: `bot`, `applications.commands`.
   - Bot Permissions: `View Channels`, `Send Messages`, `Embed Links`,
     `Read Message History`, **`Manage Roles`**.

3. **На сервере**: перетащите роль бота **выше** ролей «Кандидат» и «Отказ» —
   иначе Discord не даст их выдавать (бот честно сообщит об этом в логах и
   модератору, но роль не выдаст).

## Запуск

```bash
python bot.py
```

При старте бот: создаёт таблицы, регистрирует persistent-views, синхронизирует
slash-команды для вашего сервера, проверяет роли/права и создаёт (или обновляет)
панель заявок.

Панель можно пересоздать вручную:

```
/setup_application_panel                 # найдёт и обновит существующую
/setup_application_panel force_new: True # отправит новую
```

Команда доступна только администраторам.

## Как это работает (ключевые решения)

**Modal не поддерживает Select Menu**, поэтому UX двухшаговый:
кнопка → ephemeral-сообщение с Select → выбор режима → `interaction.response.send_modal()`
прямо из колбэка селекта. Это корректный для discord.py 2.x путь: любое
component-взаимодействие может открыть модальное окно, если на него ещё не был
дан другой ответ. После отправки формы ephemeral-сообщение с селектом удаляется,
публичного мусора не остаётся. (В discord.py 2.7 появились Select внутри модалок,
но Discord раскатывает эту возможность постепенно — используем надёжный путь.)

**Persistent-кнопки без состояния в RAM.** Кнопка панели — статический
`custom_id="application_panel:open"` + `bot.add_view()`. Кнопки модерации —
`discord.ui.DynamicItem` с шаблонами `application_approve:(?P<app_id>\d+)` и
`application_reject:(?P<app_id>\d+)`, зарегистрированные через
`bot.add_dynamic_items()`. Бот вытаскивает `application_id` прямо из `custom_id`
и читает заявку из SQLite, поэтому после перезапуска работают кнопки под любыми
старыми заявками, даже созданными месяц назад.

**Двойное нажатие невозможно.** Смена статуса выполняется атомарно:
`UPDATE ... SET status=? WHERE id=? AND status='Pending'`. Если строка не
обновилась — значит заявку уже обработали, и модератор получает
«❌ Эта заявка уже была обработана.».

**Ошибки не роняют бота.** `Forbidden`, `HTTPException`, `NotFound`, ошибки
SQLite, отсутствие канала/роли, уход пользователя с сервера, закрытые ЛС, роль
выше роли бота — всё логируется, а модератор получает честный отчёт
(«роль НЕ выдана: …», «ЛС не доставлено»). Бот не делает вид, что операция
прошла успешно.

**Cooldown переживает перезапуск**, потому что лежит в SQLite в виде Unix
timestamp, а `tasks.loop(minutes=1)` просто выбирает строки с `expires_at <= now()`.
Никакого `asyncio.sleep(7 дней)`.

## Схема БД

```sql
applications(id, user_id, mode, status, message_id, timestamp)
cooldowns(user_id PRIMARY KEY, role_id, expires_at)
settings(key PRIMARY KEY, value)     -- id сообщения панели
```

`mode ∈ {RW, FT}`, `status ∈ {Pending, Approved, Rejected}` — на уровне
`CHECK`-ограничений SQLite. Время везде — Unix timestamp (UTC).

Поведение по статусам:
- **Pending** — новая заявка не создаётся («У вас уже есть заявка на рассмотрении»);
- **Approved** — не блокирует: пользователь может подать заявку снова (например,
  на второй режим). Чтобы вернуть блокировку, поставьте `BLOCK_AFTER_APPROVAL=true`;
- **Rejected** — подача разрешена после истечения cooldown в БД.

## Чек-лист проверки

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Запуск на чистой БД | Таблицы созданы, панель отправлена, в логах нет ошибок |
| 2 | Перезапуск бота | Новая панель **не** появляется, старая обновляется |
| 3 | Нажать «Подать заявку» | Ephemeral с Select (RW/FT) |
| 4 | Другой пользователь нажимает чужой Select | Недоступно (сообщение ephemeral + проверка владельца) |
| 5 | Выбрать RW | Открывается Modal |
| 6 | Возраст `13` | «❌ Подать заявку можно только с 14 лет», записи в БД нет |
| 7 | Возраст `abc` / `1 8 лет` | «❌ Укажите возраст целым числом» |
| 8 | Возраст `18` | «✅ Заявка отправлена!», Embed ушёл в **RW**-канал |
| 9 | Выбрать FT | Embed ушёл в **FT**-канал |
| 10 | Повторная подача при Pending | «❌ У вас уже есть заявка на рассмотрении.» |
| 11 | Пользователь без прав жмёт кнопку | «❌ У вас нет прав для рассмотрения заявок.» |
| 12 | «Одобрить» | Роль Кандидат выдана, embed зелёный, кнопки исчезли, пришло ЛС |
| 13 | Повторное нажатие / второй модератор | «❌ Эта заявка уже была обработана.» |
| 14 | Перезапуск бота → нажать кнопку старой заявки | Кнопка работает |
| 15 | «Отказать» | Роль отказа выдана, embed красный, cooldown в БД, ЛС отправлено |
| 16 | Подача при активном cooldown | Отказ с меткой времени `<t:…:R>` |
| 17 | Перезапуск + наступил `expires_at` | В течение минуты роль снимается, строка cooldown удалена |
| 18 | Роль бота ниже роли Кандидат | Модератор видит «⚠️ Роль НЕ выдана», в логах ERROR, бот жив |
| 19 | У пользователя закрыты ЛС | «⚠️ ЛС не доставлено», заявка остаётся обработанной |
| 20 | Пользователь вышел с сервера | Не критично: заявка обрабатывается, cooldown удаляется циклом |

Проверить состояние БД:

```bash
sqlite3 applications.db "SELECT * FROM applications; SELECT * FROM cooldowns;"
```

## Безопасность

- Токен только в `.env`, в логи не попадает (`bot.run(..., log_handler=None)` +
  собственный форматтер, который не печатает токен).
- `.gitignore` исключает `.env`, `*.db`, `bot.log`, `__pycache__/`.
- Все проверки (возраст, права, дубликаты, владелец Select) выполняются на
  сервере в Python — UI-ограничения Discord считаются подсказкой, а не защитой.
